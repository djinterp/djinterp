vparse is djinterp's parser generator as a program and a window over one model.

  • vparse, the command line: judge a grammar, write out its program, match inputs against it, print any stage of a run as text or JSON, and save runs and run them again; measure a grammar over many inputs, make inputs from the grammar itself, and run two grammars over the same inputs to find where they differ; and have a program call its rules through a memo. It needs nothing but djinterp: no uxoxo, no Dear ImGui, no display.
  • vparse gui, the window, the workbench on uxoxo and Dear ImGui - a module the command line loads only when gui is run, built outside djinterp (build/ui/vparse, ruling 0.3 and the kit's GRAMMAR, section 7): write a grammar (in vparse's notation or in EBNF) and an input, press Run, and inspect every stage: how the grammar was read, the rules it became, the generator's plan, the program, the rules that matched, where the parser spent its work, and the machine's trace step by step. Every run is kept for the session, any two runs can be compared part by part, and runs can be saved to folders and loaded back.

The command line and the window drive the same model, so a part vparse prints is the part the window shows, row for row, and a run either one saves the other loads. The model drives djinterp's own vparse, djinterp::parsegen::vparse, through its session: a grammar is built and run only once the session has accepted it, and refused in the session's words when it has not.

It is one of djinterp's tools, laid out as bitwisedom is: the program in djinterp's tree, its window beside it under inc/ui, src/ui, tests/ui and build/ui.

The namespaces are vparse::workbench for the model and the window, and vparse::cli for the command line. The library it drives is djinterp's, in inc/, src/ and tests/djinterp/parsegen/vparse; its guide is docs/djinterp/tools/vparse/vparse-AGENTS.html, and the session is session.hpp there. The command line is made on djinterp's command-line kit, tools/cli (its README.html and GRAMMAR.html), over djinterp's argument parser, parse/cli/arg_parser, CLI11's design in C; the window, a module, reads its arguments through the same kit, as a program the command line made.

Before the first build

  • djinterp is this tree. The build finds djinterp's root from where it sits, five folders below it, and needs no setting. It needs the argument parser's sources, src/djinterp/parse/cli/arg_parser/c/, which are still being written, and the command-line kit's, src/djinterp/tools/cli/c/, with the kit's CMake module, build/cmake/djinterp/tools/cli/ DjinterpCli.cmake, which makes it: the command line uses the parser's validators, its completion scripts and its response files, through the kit. The build tests the parser with its own suites when its test leaf is there; the kit's suites are run from the kit's own leaf, which names its testing libraries as this build names the programs' and so is not added here.
  • uxoxo is needed for the window alone, and only the window's build, build/ui/vparse, looks for it: the tree of 2026.10.16 or later, two directories above djinterp's root - as uxoxo/uxoxo-project or uxoxo
    • or at UXOXO_ROOT, with its Dear ImGui under inc/imgui (uxoxo carries 1.92.8 there, laid out as Dear ImGui's repository is). uxoxo builds itself, from its build/cmake/CMakeLists.txt; the window's build adds that as a subproject. Configure checks for the build, the fifteen uxoxo headers the window includes and Dear ImGui, and names whatever is missing. djinterp's own build of vparse names no uxoxo.
  • Stale files. A tree that was only ever unzipped over still holds the parse and parsegen C layer from before it moved into c/, which defines every function its successor does. This build never compiles those files, and configure warns while they are there, naming them. The retire scripts in djinterp's _retired/ take them out of the way.

Flags

Code this build owns, the tool's and djinterp's, is built at its level with the conformance flags djinterp's ladder uses (-pedantic-errors -Werror=undef, -D_XOPEN_SOURCE=700 on POSIX), -Wall -Wextra -Wshadow -Wcast-qual, and, for the tool's own sources, the rest of the style guide's baseline: -Wconversion, and under Clang -Wreserved-identifier and -Wdocumentation; /W4 under cl. Under a cl-style driver every unit that reads djinterp's headers is given the same reading flags, uxoxo's included: /utf-8, /Zc:__cplusplus, /permissive-, /EHsc, and for cl itself /Zc:preprocessor. Dear ImGui is given /utf-8 alone.

Whose headers are judged. The tool includes its own headers by a path relative to the file, as djinterp's tree does, and djinterp's, uxoxo's and Dear ImGui's through their include directories, which this build passes as system ones. GCC and Clang judge a header by how it was found, so the tool's own headers are held to its warnings and its dependencies' are not. cl judges a header by where it is, and the model's three headers sit in djinterp's inc/, so under cl they are read as external, at /external:W0: the GCC and Clang builds are the ones that check them.

<windows.h>. This build defines no Windows macro. wingdi.h defines ERROR, and djinterp's LR family has an opcode called ERROR, so a unit that includes <windows.h> and then lr.hpp does not compile. None does today: host_win32.cpp includes no vparse header, and the command line's main.cpp includes <io.h> and <fcntl.h> alone. The cure is the opcode's name, in djinterp: branch vparse/lr-reject renames it REJECT.

The command line

bin/tools/vparse/vparse-linux64 [OPTION]... COMMAND [ARGUMENT]...

It is made on djinterp's command-line kit, and its grammar is the kit's GRAMMAR.html, section 11. It has what every djinterp program has (section 6 there): -h and --help, after the program or after a command; --version, and with -v how the program was built; -q, -v and --color, before the command or after it; and the help and completion commands. Its help is laid out as GNU programs lay theirs out, and each command's help ends with what its exit status answers.

command does ends with

Every failure is said as the kit says one, on standard error, and ends with 2: vparse: error: MESSAGE. A command line that cannot be read is a usage error, the command's name before the message and a pointer to its help after it:

vparse: error: match: standard input can be read once: - may stand for the grammar or for one input
Try 'vparse match --help' for more information.

A file that cannot be read or written says which and why - vparse: error: cannot read 'expr.txt': No such file or directory - and an output that takes nothing says so: cannot write standard output: No space left on device. A grammar the session refuses is said after its name, in the words of the run's headline:

vparse: error: expr.txt: the program could not be built: rule not defined: Atom

and, where its reader stopped at a place, after the place, as a compiler says one and an editor turns into a link - the place taken out of the words, which the JSON's error and the run's result still hold whole:

expr.txt:2:12: error: the grammar could not be read: the reader stopped, inside Grammar > Rule, expecting ';' or '|'

The EBNF reader says what it expected and not where, so its refusal has no place: vparse: error: expr.ebnf: the grammar could not be read: expected ';'.

check, compile, match and the measures then print nothing more but, with --format json, their JSON; run and replay print the run all the same, since its parts show how far it got. A refused grammar is trouble, 2, to every command but check, whose answer it is: 1. Every command reads every file it is given before it runs, and writes its output only once the output is whole, so a command line that fails prints the failure and nothing else.

vparse check expr.txt
vparse match expr.txt --text 1+2 '(3*4)-5' 6/
vparse run expr.txt input.txt -p rules,program,heat
vparse run expr.ebnf --text '2*(3+4)' -p all --format json
vparse match expr.txt corpus/*.txt --save --root runs
vparse replay runs/session-20261016-101500/run-003 -p trace
vparse run expr.txt input.txt -p summary,profile --memoize auto
vparse corpus expr.txt --walks 200 -o corpus
vparse bench expr.txt corpus/*.txt --memoize auto --format json
vparse compare expr.txt expr_factored.txt --walks 200
vparse compare expr.txt expr.txt --memoize all
vparse completion bash > vparse.bash

A run is counted as it runs, traced or not: its profile part has a row a rule - its calls, the calls that repeated one at the same position and the steps those ran, the memo's answers, and its steps, arrivals and revisits, the heat map's counts - and the summary says how deep each stack went and what the memo did. A corpus input that ends in -walk.txt was derived from the grammar's rules, and one that ends in -miss.txt is a walk with a character deleted, inserted or replaced; derived is not accepted, since ordered choice can refuse what the rules derive.

JSON

--format=json prints one JSON document, whatever the command, ended by a newline: an object whose members come in the order the tables below give. A document only grows (the grammar's R19): a key, once written, keeps its meaning, and a new key comes after the ones there. The suite holds every table here to what the command writes, key for key and in order (tests_cli_json), so a key the code adds and the README does not is a failing test.

JSON is UTF-8: a byte that belongs to no UTF-8 sequence, which a grammar or an input may hold, is written as the visible escape \xHH the listings use for control characters. A count is a whole number; a time, ms, is milliseconds with three decimals. A grammar's or an input's name is the one text prints: a file's name as given, standard input for -, and an input given as text quoted and clipped, '12+3'; its argument is the command line's own word.

The screen

The toolbar holds Run (also Ctrl+Enter, from anywhere), the front end (notation or EBNF), whether to record the trace, and the step limit of the run over the input.

The left column has the grammar and input editors, the list of runs (newest first, green if the run matched, red if not), and the file controls.

The right side shows the selected run: a sentence saying what happened, the tape, and a tab for each part of the run.

The tape is the text as a strip of character cells. The rules that matched are drawn beneath it as nested spans, one layer per depth. The highlighted cell is where the machine was at the current trace step; move it with the slider, the arrow buttons, the arrow keys while the pointer is on the tape, or by clicking a character, which jumps to the first step that reached it. When a run fails, the furthest point the parser reached is framed in red, the text after it is greyed, and the run opens at the step where it failed there. When the grammar itself cannot be read, the tape shows the grammar instead, with the reader's failure marked the same way.

Comparing runs. Click vs beside another run to compare it with the selected one. Each tab then shows both runs side by side, and rows that only one of them has are washed red, with a count above each side. Program rows are compared by what they mean, not where they sit: calls by the rule they call, branches by rule and offset, so adding an alternative marks the new instructions and not every address after them. Traces are shown side by side without marking. On the Heat tab the two maps share one colour scale, so a grammar that re-parses less shows up paler.

How it is put together

  • The model (run, store, heat) runs the stages and describes them. A grammar that reads is offered to djinterp's session, which accepts it or refuses it in its own words; an accepted grammar is then built here with every stage kept. A program here of another length than the session's is a fault the run reports, and the suites hold the two to the same disassembly. The notation grammar is read the way notation::parse_grammar reads it, under the same step limit, notation::read_limit, but on a traced machine, so the reading can be inspected like any other run; a reading that stops untraced is read again, traced, so that it can always say where. The matched-rule tree, the failure frontier and the heat map are recovered by replaying the trace; every pass is also counted as it runs, so a run's profile needs no trace. Where the request names a memo, the program is made to call those rules through it once the session has accepted the grammar; the trace readers see a MEMO the memo answered for what it was, and replay the spans its rule's first match closed, so a memoized run's matches are the plain run's.
  • The command line (cli/) is a tree of subcommands on djinterp's argument parser. Each subcommand reads its files, runs the model's execute(), the function the window's Run button calls, and prints the model's own listings, as text or as JSON (report). A trace is recorded only for what it explains: match runs each input untraced and a failed one again, traced, to say where it stopped; check and compile never trace. The measures (measures.cpp) build a grammar once, through the same execute(), and run the library's machine over the inputs themselves, untraced, counting each run and timing it apart.
  • The window's face (ui/vparse/view, ui/vparse/elements) is a uxoxo template over the model: one shell with holes for the toolbar, editors, runs, files and detail, closed each frame with uxoxo's closing pass. update applies an event to the model. The workbench's own elements, listing, tape and heat, are uxoxo element modules; their attributes key and target mean what they mean on every uxoxo element.
  • The renderers (elements_imgui.cpp) draw those elements on uxoxo's Dear ImGui platform, registered through set_renderer, with the theme.
  • The host (host_*.cpp) opens the window, runs a frame, and reads one back for --screenshot; plugin.cpp, the module's run function, reads its command line through the kit and is the loop between them.

Limits

  • A notation literal is one character, 'a', so EBNF's "ab" is 'a' 'b' there. Notation character classes take only letters, digits and -, so [+-] does not read; write '+' | '-'. EBNF classes are wider.
  • PEG has no left recursion: a left-recursive grammar loads, and a run over it loops until the step limit stops it, which the command line and the window both say.
  • Both frontends read a grammar as PEG: | is ordered choice, so S = "a" | "ab" (in EBNF) never matches ab, and S = A* A never matches, since the repetition takes every A.
  • The trace keeps every step in memory. Runs of a few hundred thousand steps are fine; the step limit bounds a run over an input, and a traced reading of a grammar takes about fifteen steps a byte of it: a grammar of 5,000 rules is two million steps and some 360 MB traced, and a tenth of a second and 34 MB with the trace off.
  • --memoize auto counts a run without the memo before it chooses, so the choice costs what the run it saves would have: over nested.txt at depth 7, ten seconds for a run of 183 steps.
  • A profile costs a run about half again its time; the trace costs far more. The memo keeps every result to the end of the run, in pages of 256 positions for each rule it is used for.
  • The heat map gives each input character a column up to 160 of them; longer inputs share columns, each covering a range of characters.
  • EBNF is read by a hand-written parser rather than the machine, so its reading has no trace.
  • Comparing very long listings (over four million row pairs, once the common start and end are set aside) falls back to comparing row by row.
