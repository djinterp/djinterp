Building from the djinterp tree

bitwis(e)dom is two builds, since its window is made with uxoxo, which the djinterp tree does not hold (2026.10.23):

  • the command line - the model, bitwisedom, bitwisedom-gen and their tests - from build/cmake/djinterp/tools/bitwisedom, which needs djinterp alone;
  • the window - bitwisedom-gui, the module bitwisedom gui loads, and the smoke test that drives it - from build/ui/bitwisedom, which builds the command line's build within it, then uxoxo, then the module beside the program. The window's sources lie beside djinterp's, not in them: inc/ui/bitwisedom, src/ui/bitwisedom, tests/ui/bitwisedom.

Run the CMake presets from the build's directory (not the repository root); for everything:

cd build\ui\bitwisedom
cmake --preset msvc
cmake --build --preset msvc-release
ctest --preset msvc-release

Build intermediates remain in out/msvc/ under that directory. Release binaries go to <djinterp>/bin/tools/bitwisedom/, and Debug binaries to <djinterp>/bin/tools/bitwisedom/debug/, each named with a platform tag: bitwisedom-win64.exe, and beside it the window's module, bitwisedom-gui-win64.dll, where bitwisedom gui looks for it. DJINTERP_ROOT defaults to the containing djinterp checkout; UXOXO_ROOT, which only the window's build reads, to the environment's UXOXO_ROOT, then to the sibling checkout - uxoxo, or uxoxo/uxoxo-project, beside djinterp's checkout - and never to a directory inside djinterp's tree (the roots, below).

Building bitwis(e)dom

Two CMake projects in vparse's shape. The command line's takes djinterp from its root by absolute path and builds the model, the generator, the command line and their tests; the window's includes it, takes uxoxo from its own root, and builds the window's module and the smoke test.

It is written for the consolidated djinterp of 2026.10.07, with the owner's edits since, and the uxoxo of 2026.10.14 with Dear ImGui's docking branch in its inc/imgui - the uxoxo overlay of 2026.10.18, which replaces that directory and nothing else. The window's sheets and tool windows dock, float and tab as Visual Studio's do, and those are the docking branch's: ImGui 1.92.8 WIP, its docking branch at dee5bf3e. Before 2026.10.18 it was written for the uxoxo of 2026.10.11 - uxoxo_2026_10_11b.zip, whose blueprints share their drawing, so a tree of a thousand rows is realized in linear time.

Before the first build

  1. uxoxo's Dear ImGui is the docking branch (2026.10.18): its inc/imgui/imgui.h defines IMGUI_HAS_DOCK, or configure refuses it by name. The uxoxo overlay of 2026.10.18 puts it there; nothing else of uxoxo changes, and uxoxo's own elements build on it as they did. uxoxo is otherwise the updated one, of 2026.10.11 or later. (The window's build alone reads uxoxo.) bitwis(e)dom's window uses uxoxo's number, combo, colour, tree, menu, section, table and splitter elements, element keys and targets, and uxoxo's own build at build/cmake/CMakeLists.txt - since 2026.10.09, its popup element (the context menus), a tree node's rename in place and its right-click and double-click actions, and a text field that reports only when its edit is done - and, since 2026.10.11, its window element (the bottom panel floating, or opened over the grid), the buttons at a tab bar's end, line splitters and flush columns. The uxoxo of 2026.10.09 lacks the window, and configure refuses it by name (element_window.hpp is missing), as it does the uxoxo of 2026.10.07, which lacks the popup as well, and the uxoxo uploaded before 2026.10.04, which lacks everything.
  2. djinterp is the consolidated tree of 2026.10.07. bitwis(e)dom reads its headers - the environment layer, the root's kit, and re_std's integers and bit functions - and, since 2026.10.09, compiles nine C sources of its parse layer: the C and C++ lexer, its literal decoder and the diagnostic sink they report into, with which it reads macro bodies, imported headers and environments. A djinterp without them is refused by name, with the files it is missing. Nothing else of djinterp is compiled, so the leftovers an unzip leaves in djinterp's tree do not concern it (vparse's BUILD.html has the two scripts that retire them).
  3. Off Windows, GLFW 3.3 or later for the window (libglfw3-dev, brew install glfw, vcpkg install glfw3). On Windows the window is Win32 + Direct3D 11 and needs nothing beyond the Windows SDK. Without GLFW, or without uxoxo, build the command line alone, from build/cmake/djinterp/tools/bitwisedom: it needs neither, and bitwisedom gui then says the window is not installed, where it looked for it.

Quick start

On Windows, from a Developer Command Prompt (so cl is on PATH), in build\ui\bitwisedom:

cmake --preset msvc
cmake --build --preset msvc-debug
ctest --preset msvc-debug
..\..\..\bin\tools\bitwisedom\debug\bitwisedom-win64.exe gui

vs2022 makes a solution for the IDE instead; clang-cl and strict (clang-cl, warnings as errors) are there too. The command line's build, in build\cmake\djinterp\tools\bitwisedom, has the same presets, and its programs are five directories down from the root rather than three.

Elsewhere, in build/ui/bitwisedom - naming uxoxo's root only where it is not the sibling checkout beside djinterp's:

cmake --preset clang -DUXOXO_ROOT=/path/to/uxoxo
cmake --build --preset clang-debug
ctest --preset clang-debug
../../../bin/tools/bitwisedom/debug/bitwisedom-linux64 gui

gcc is the same with GCC; clang-strict is the loudest configuration; mingw-cross builds a Windows bitwisedom.exe, and from the window's build its bitwisedom-gui.dll, on Linux (see below).

The roots

variable default must contain
DJINTERP_ROOT the djinterp checkout the build is in inc/djinterp/djinterp.hpp
UXOXO_ROOT the window's build only: the environment's UXOXO_ROOT, else the sibling checkout beside djinterp's - uxoxo, else uxoxo/uxoxo-project, then both a level up - never inside djinterp's tree inc/uxoxo/element.hpp, build/cmake/CMakeLists.txt
BITWISEDOM_ROOT djinterp's root

The djinterp root is found from the build's own directory. uxoxo is looked for beside djinterp's checkout - uxoxo, then uxoxo/uxoxo-project - and then the same a level up, where a directory of projects keeps each project's checkouts in a folder of its own: a djinterp checked out at D:/sam/code/projects/frameworks/djinterp/release finds uxoxo at D:/sam/code/projects/frameworks/uxoxo/uxoxo-project, the path that was the default before; one not found names the places it looked. Each root is checked at configure time (build/ui/bitwisedom/cmake/UiRoots.cmake for the window's), and a wrong one is one message naming the variable to set.

Language levels

bitwis(e)dom's floor is C++17, the floor of the uxoxo and djinterp headers it stands on (djinterp's free monad and option record). BITWISEDOM_CXX_STANDARD picks 17, 20 or 23 for the build, default 20, and passes it to uxoxo as UXOXO_CXX_STANDARD. Below the floor every bitwis(e)dom header is empty rather than an error, as djinterp's are below theirs.

The model's suite is built at every level from the floor the compiler can select, whatever the build's own level is.

Flags

bitwis(e)dom's own sources - the model, the generator, the window, the tests - are held to the style guide's whole baseline: -Wall -Wextra -Wshadow -Wcast-qual -Wconversion under -pedantic-errors and -Werror=undef, and under Clang -Wreserved-identifier and -Wdocumentation as well (under cl, /W4). BITWISEDOM_WARNINGS_AS_ERRORS=ON makes them errors.

The dependencies' headers - djinterp's, uxoxo's, Dear ImGui's, GLFW's - are system headers to bitwis(e)dom's targets, so their warnings are not counted against it. uxoxo builds itself with only its level and /utf-8. djinterp's lexer is compiled as C99, djinterp's floor, with no extensions and no warnings asked for - under cl, with /utf-8 and the conforming preprocessor.

djinterp's lexer headers have no extern "C" guards of their own, so bitwis(e)dom includes them inside one (src/clex.cpp), and they are read nowhere else. That is a gap in djinterp worth closing there: a C++ unit that includes them bare links against names it cannot find.

Under a cl-style driver: /utf-8 (the trees are UTF-8 without a byte-order mark), /Zc:__cplusplus, /Zc:preprocessor, /permissive-, /EHsc, /bigobj (the interface's units hold enough lambdas to run a Debug object past cl's section limit), and _CRT_SECURE_NO_WARNINGS for std::localtime.

BITWISEDOM_HOST (auto, win32, glfw) chooses the window's host; auto is win32 on Windows. GLFW on Windows works too, where uxoxo's build finds it. The module is a shared object linking the model, the kit, uxoxo and Dear ImGui, so the window's build compiles everything position-independent; of its own, it exports its entry point alone, so its copy of the model never binds to the program's.

bitwisedom gui [SHEET]... opens the window on the sheets named - example:NAME, or any file the window opens, a header to import among them - or where it was left. Its operands are read by the commands' rules, so a name that is no example, or a file that cannot be read, is refused before any window opens, in the commands' words. --size=WxH and --scale=S set the window's size and the display's scale; --do, --screenshot, --frames (the GLFW host) and --warp (the Win32 host) are for building and testing, listed under their own heading in bitwisedom gui --help. On Windows, a console made for the run alone - a shortcut's - is let go when the window opens.

The two fonts - Roboto Medium for the interface, Cousine for values and code, both Apache 2.0 - are compiled in, from the copies uxoxo's ImGui carries, as byte arrays: ImGui's base85 form is one string literal, past cl's 64 KB limit (C2026).

After unzipping an overlay

An overlay unzipped over the trees keeps the times its archive holds, and those can be older than the objects of the last build. A build that went by the times alone would take the old objects for the new sources, and the tests would run the code of the overlay before: model_c++17, _20, _23 and ui_smoke then fail, since each overlay that adds sections raises the count they must print (passed: 36, passed: 44) while the old programs print the old one.

So configure after unzipping - cmake --preset msvc, as the quick start does - and then build. Each configure keeps a hash of every source it watches in the build tree - bitwisedom's and the kit's in bitwisedom_sources.sha1, and in the window's build the window's and uxoxo's with its Dear ImGui in bitwisedom_ui_sources.sha1 - and touches each whose content changed since the last configure, so the build compiles it again (cmake/Freshness.cmake); it says how many it marked. A build tree configured before it kept any hashes has every source marked once, and compiles them all. Only the times of changed files are changed. Where a file cannot be touched, configure names it: build with --clean-first (cmake --build --preset msvc-debug --clean-first), which a build tree in any doubt can do as well.

If the window draws stray pixels

bitwisedom-win64.exe gui --warp draws with WARP, Microsoft's software rasterizer, instead of the GPU, and says so in its title. Stray pixels on the GPU that WARP does not draw are the GPU driver's; pixels WARP draws too are the drawing's. ui_smoke checks every frame for what a GPU may draw as stray pixels - a vertex that is not a number, one far past any window, or one outside the font atlas - and the grid's lines are cut to what the window shows: a line across a sheet of 65,536 bits once ran a million pixels past it.

How uxoxo is found

Only the window's build reads uxoxo. build/ui/bitwisedom/cmake/UiRoots.cmake finds it (the roots, above), and cmake/Uxoxo.cmake beside it checks it and adds ${UXOXO_ROOT}/build/cmake as a subproject, after the command line's build. uxoxo's build takes djinterp from the djinterp::headers target the command line's cmake/Djinterp.cmake defines, and gives back uxoxo::uxoxo, uxoxo::imgui, and whichever backends it can build: uxoxo::imgui_win32_dx11 on Windows, and uxoxo::imgui_glfw_opengl3 where it finds GLFW. uxoxo's own tests stay off unless BITWISEDOM_BUILD_UXOXO_TESTS=ON.

uxoxo's Dear ImGui must be the docking branch (IMGUI_HAS_DOCK), or configure stops. Its imgui.cpp and imgui_internal.h carry a patch of uxoxo's, marked [uxoxo] and announced by IMGUI_DOCK_TAB_BAR_INSET:

  • 1, uxoxo's own since 2026.10.25 and the one 0.9 takes (ruling cli e): ImGuiDockNode::TabBarInsetLeft, a dock node's tab bar begun inset. The Options can set a sheet's tabs over one of its columns; they begin at the column's left and run on to the right edge. Configure says so, the tab menu offers no more, and the Options say so.
  • 2, the overlay of 2026.10.20: TabBarInsetRight and TabBarAlignRight as well, the bar ended inset and kept to its right. The tabs then end where the column does, at its left or its right.
  • Neither: configure warns, and the tabs run across the whole width from the left, as Dear ImGui's own do and as they do by default.

Cross-compiling for Windows

cmake/toolchains/mingw-w64-x86_64.cmake, in the command line's build, builds a self-contained Windows bitwisedom.exe and bitwisedom-gen.exe on Linux with MinGW-w64 (the posix thread model), and from the window's build, whose mingw-cross preset takes the same file, a self-contained bitwisedom-gui.dll beside them - MinGW's runtime linked into each, so no DLL of it need ship:

cmake --preset mingw-cross
cmake --build --preset mingw-cross-release

The toolchain keeps CMake's package searches and pkg-config inside the MinGW sysroot; without that, the build machine's GLFW is found and offered for a Windows target.

Later still on 2026.10.20, a build under MSVC reported one section of the smoke test failed - "code in and out", at the code a new sheet is made from - and the rest passed. The section copies a row as code and, at once, puts other code on the clipboard to make a sheet from; and on Windows ImGui's clipboard is the system's, whose every copy a program watching it - the clipboard history, a remote desktop, a password manager - opens it to read, so a copy straight after another can fail without a word, and the section read the row's code instead. The smoke test now keeps a clipboard of its own, in memory, in every ImGui it makes, as ImGui itself does off Windows; it no longer touches the user's clipboard either.
