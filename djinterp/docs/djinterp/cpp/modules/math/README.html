djinterp::math

The math subframework: scalar kernels, intervals, linear algebra, coordinate systems, geometry, and (in progress) expressions, functions and calculus. Everything is header-only. The numeric work is written once in C, under inc/djinterp/c/modules/math/; the C++ headers under inc/djinterp/cpp/modules/math/ are faces over it that add what each language level allows.

This file says what is here and how to build and check it. roadmap.html, beside it, says what comes next and in what order; decisions.html holds every decision the lane has taken, S1 on, each with its alternative and a review of it, its advantages and drawbacks and the path recommended, the outstanding ones first, by group and urgency; and comparison.html compares the framework as proposed with similar libraries, feature by feature.

Quick start

Include the header of each part you use, as below, from C++11; math.hpp includes every header of the module, at every level, each part from the level it begins at: the compile-time core, the forms on it, the calculus headers and reify from C++11 (chunks 53, 56, 58 and 59), empty below it.

#include "djinterp/cpp/modules/math/expr/expr.hpp"              // the language
#include "djinterp/cpp/modules/math/complex.hpp"                // complex<T>
#include "djinterp/cpp/modules/math/quaternion.hpp"             // quaternion<T>
#include "djinterp/cpp/modules/math/linear_algebra/linalg.hpp"  // linalg

namespace m  = djinterp::math;
namespace la = djinterp::math::linalg;

// a formula as text: parsed once, then evaluated, exactly or in a type
const m::expr  f = m::parse("x ^ 2 - 2 * x * y + y ^ 2");
const double   d = f.eval<double>(m::at("x", 0.5).at("y", 2.0)).value();
const m::value h = m::parse("1/3 + 1/6").eval().value();   // exactly 1/2
const m::value r = m::parse("sqrt(-4)").eval().value();    // exactly 2im

// compiled once for a type, then run many times, the same bits as eval
const m::expr_program<double> p = f.compile<double>().value();  // x, y
const double                  xy[2] = { 0.5, 2.0 };
const double                  q = p.run(xy);                    // 2.25

// one number of any kind, exact where it can be
const m::value tenth = m::value(1) / m::value(10);
const m::value sum   = tenth + tenth + tenth;                 // exactly 3/10

// the C core's faces: complex numbers, quaternions, linear algebra
const m::complex<double>    z(3.0, 4.0);                      // abs(z) is 5
const m::quaternion<double> turn =                            // a quarter
    m::from_axis_angle(la::vector<double, 3>(0.0, 0.0, 1.0),  // turn about
                       1.5707963267948966);                   // z
const la::vector<double, 3> v =                               // about
    m::rotate(turn, la::vector<double, 3>(1.0, 0.0, 0.0));    // (0, 1, 0)
const double                a_[4] = { 2.0, 1.0,
                                      1.0, 3.0 };
const double                b_[2] = { 3.0, 5.0 };
const la::vector<double, 2> s =                               // (0.8, 1.4)
    la::solve(la::matrix<double, 2, 2>(a_), la::vector<double, 2>(b_));

Each value in a comment is what the program quickstart_c48.cpp of chunk 48's record prints, built with g++ and clang++ from C++11 to C++20. A step of the language that can fail returns expr_result<T>, its answer or an expr_error; value() takes the answer, and an error passes through every step chained after it.

2. Architecture

A C core with C++ faces. Every algorithm lives once in the C layer, and C programs call it directly. The C++ headers forward to it instead of restating it. Element types the C core does not cover (anything other than float, double and long double) take a generic C++ path. These are the owner's rulings of 2026.10.04.

Kernels. A kernel is a function defined in a header, marked with one of five qualifiers from c/modules/math/math_common.h:

  • D_MATH_FN: pure arithmetic. A static inline function in C, and an inline one in C++ that is constexpr from C++14.
  • D_MATH_FN_RT: calls the C library or writes to a buffer, so it is never constexpr.
  • D_MATH_FN_ENTRY: a function a table points to, as a boxed kind's entries are. A header inline the compiler is never told it must inline, as it is told the other two's outside testing builds, so a call through the table builds at every optimization level, gcc's -Og included (chunk 26).
  • D_MATH_FN_KERNEL: a large kernel of pure arithmetic that many functions share, as cplx.h's long double kernels serve its three families: constexpr from C++14, as D_MATH_FN is, but never forced inline, so that a translation unit compiles it once however many callers it has (chunk 37).
  • D_MATH_FN_KERNEL_RT: such a kernel that calls the C library, so never constexpr: the eigenvalue paths' plain forms (chunk 38).

Two forms of each function.

  • The _c form (d_math_d_sqrt_c) is pure arithmetic and a constant expression from C++14. It is correctly rounded for sqrt, cbrt, hypot, fmod, remainder and the rounding functions, and within an ulp of the C library for the transcendental functions.
  • The plain form (d_math_d_sqrt) calls the C library and is fast at run time.

A face picks one form per language level, using std::is_constant_evaluated from C++20. For the correctly rounded functions the two forms are bit-identical. Domain errors give the C library's answers in both forms: NaN, or minus infinity for log(0). In C++ each header ends with one overloaded name for all three families (d_math_sqrt_c(x)).

One operation per statement. Kernel bodies compute one operation per statement. This keeps x87 excess precision and FMA contraction from changing results, so every build in the matrix computes the same bits. Clang on the 32-bit x87 is the known exception, and stays out of the matrix (S37). It is not enough where gcc fuses across statements, as it does in its GNU modes wherever the target has a fused multiply-add: there each exact product takes its low part by an explicit one, the bits Dekker's product gives elsewhere, and every generated header tells clang not to fuse (S414); the plain formulas, the _fast forms among them, follow the build (S415). The double family's correctly rounded functions refuse to compile where double is evaluated wider than double, as on a 32-bit x87 (S418).

Generated code. Twenty of the core headers are generated by scripts/gen_c_math_float.py, each from one template written out for each family (f, d, ld). Edit the generator, never its output. --check fails if the headers are out of step. math_common.h, interval.h, rational.h, value.h, decimal.h, literal.h, wide.h and value_wide.h are written by hand. The generator is a package, scripts/gen_c_math/, of modules of at most about 4,000 lines, one for a header's text or two, and the script runs them (S439). It writes the eight largest headers in parts of at most about 4,000 lines - decomp.h in ten, cmat.h in seven, exponential.h in six (S502), cplx.h and quat.h in five, vec.h, coord.h and mat.h in four - each part a header that stands alone, named for its header and what it holds (decomp_f.h, decomp_f_eigen_c.h, ..., decomp_cpp.h), and the header of the name includes them in order, so that an includer sees the same code in the same order (S436). It aligns each parameter list's names (S435).

Exact rationals. rational.h holds rationals over the widest integer, dj_math_imax, in one reduced form. Each kernel either stores the exact result or stores nothing and says why: overflow, a pole or an invalid operation. Overflow means that the reduced result does not fit, never that an intermediate did not: intermediates are held in two words. A rational converts to the nearest float, double or long double, ties to even, whatever the rounding mode.

The generic value. value.h's struct dj_math_value holds one value of any kind: none, an error, a boolean, an integer, a rational, a float, a double or a long double. Its operations follow a tower:

  • Exact numbers stay exact. A rational whose denominator comes to 1 is an integer. An exact result too wide for dj_math_imax becomes the nearest long double, flagged inexact, until bignum exists.
  • An exact number meeting a floating-point one is converted to the latter's type, correctly rounded. Two floating-point kinds meet in the wider.
  • Errors are values that pass through operations. A boolean or none in arithmetic is a domain error.
  • Comparison is exact across kinds.

Boxed kinds. A kind of number that does not fit in the value, such as a wide integer or a big float, is boxed. It fills in a table, struct dj_math_boxed_kind, which is how it registers:

  • its name, and its rank: its place in the tower, on one scale with the inline numbers (integer 100, rational 200, float 300, double 400, long double 500), and its own;
  • whether it is a number, and whether an exact one;
  • its operations: retain and release, arithmetic, comparison, conversion to the inline numbers, and text.

A boxed value holds a pointer to its kind's table and one to its storage, so value.h needs no list of kinds and keeps no state. In an operation, the operand higher in the tower handles it. A boxed kind does so through its table. An inline number converts the boxed operand to its own kind; to compare, it uses the nearest long double and the rounding's direction, so comparison stays exact. A result is the caller's to release with d_math_value_release, and an operand is only lent. A new kind changes neither value.h nor the inline kinds' code, and the inline kinds are still constant expressions.

This is roadmap Phase 1's C core; its C++ face is math::value (below).

Wide integers. wide.h holds signed integers of 256 bits: a magnitude in limbs of half a word (32 bits, or 16 where the build has no 64-bit integer) and a sign, so the range is symmetric and 0 has one form. As in rational.h, each kernel stores the exact result or stores nothing and says why: overflow, division by zero, 0/0, a rational that is no integer, or text that is no integer. Division truncates, as C's does. The kernels are add, subtract, multiply, divide with remainder (Knuth's algorithm D), gcd, comparison, conversion to and from dj_math_imax, dj_math_umax and rationals, text both ways, and the nearest float, double or long double, ties to even, with the rounding's direction; a float past the largest is an infinity. Nothing allocates, and every kernel but the text writer is a constant expression from C++14. Under the type are limb kernels that take any length, which its boxed kind (below) and bignum's later kinds build on. This is roadmap item P1.

The wide integer as a value. value_wide.h registers wide.h's integer with value.h as a boxed kind, the first real one, and value.h did not change. Its rank is 210, between the rational's and the float's. d_math_value_from_wide makes a value of it, and d_math_value_to_wide reads an integer back. With a wide integer, an inline integer or a rational, its arithmetic is exact:

  • an integer stays a wide integer, however small, so that arithmetic begun with one stays exact past dj_math_imax;
  • a result that is no integer is an inline rational, where it fits the family;
  • a result past both, an integer of more than 256 bits or a ratio past dj_math_imax, is the nearest long double, flagged inexact (G2), rounded once from the exact ratio, whose terms run to 512 bits, by wide.h's division.

A float, double or long double meets it as value.h has an inline number meet any boxed kind: converted to the nearest value of its type, so a comparison stays exact too. Each value is a box of its own, allocated through two knobs in config/c/modules/math/cfg_value_wide.h (malloc and free unless set otherwise); where no storage is given, the result is a memory error.

The value in C++. math/value.hpp is the value's face. math::value holds one value of any kind, a boxed kind's included, and holds its box as an int holds its number: a copy is one holder more, and a value destroyed or overwritten one fewer. From C++11 a value moves, and a move never fails. math::inline_value holds the inline kinds alone, never a box, so it is a literal type, and its operations are constant expressions from C++14; from C++20, where a destructor may be constexpr, math::value's are too, for the inline kinds. Both are made implicitly from the arithmetic types, a bool and an error code, and refuse a pointer: an unsigned integer past dj_math_imax is G2's long double, through value.h's d_math_value_from_uint. Their operators, abs and the six comparisons are found by argument-dependent lookup only, and an operation makes its result in place from value.h's, so it costs what value.h's call does. Each comparison asks value.h's exact order, so a NaN, an error and unlike kinds are unordered, and from C++20 <=> is a partial ordering. to(out) converts a value where it has one of out's type. From C++20 the concept number names the types generic code computes with: the arithmetic types but bool, and the two values.

Numbers in generic code. math/number_traits.hpp is the static side of the value. number_traits<T> says what a template needs of a number type: whether its arithmetic is exact, whether it holds integers alone, whether its quotients are a field's and its products commute, its zero and one; whether < orders it, and |x|; the magnitude generic code pivots by, |x| for an ordered type and a nonnegative number of an ordered type for one without an order (a complex number, a quaternion); its square root, exact for an integer type, rounded down; its conversions to and from double; its epsilon, the precision a value carries, 0 for an exact one; and its tolerance, four epsilons relative to the larger magnitude, 0 where both values are exact (chunk 38, S303). The C++ face's comparisons given no tolerance take it, relative to their operands' scale; given one, they take it as an absolute one, as before (S304). The standard integer and floating-point types have their own; math::value and inline_value theirs, whose root is exact for the square of a rational of the family, so the norm of (3, 4) is 5; and any other type, a bignum among them, joins by specializing it. A type with none is taken as the linear-algebra subframework always took one: made from an int, and through double; an integral type with none, a character type or bool, is exact and an integer, as the language has it. common_number<A, B> is the type of a + b, from C++98: the usual arithmetic conversions for the arithmetic types, and for the values the classes' own. Linear algebra's generic path, for any element type but float, double and long double, now reads its zero, one, roots and tolerances from the traits, and a vector or matrix made by default is zero in any number type, so vectors and matrices of math::value compute exactly: the Hilbert matrix's determinant and inverse come out as rationals, its product with its inverse the identity. The generic kernels keep each product in its order and pivot by magnitude, so that solve and inverse of a quaternion matrix are right, and solve(A, b) and solve(A, B) take every number type but an integer one, by elimination of [A | B]: for float, double and long double the C core's d_mat_solve, LU's solution refined with extra precision (chunk 38, S302, S305; chunk 49, S406), for math::complex<T> cmat.h's d_cmat_solve, refined the same way (chunk 50, S411), and solve_fast the elimination alone, LU's bits.

The run-time expression language. math/expr/ is roadmap Phases 2 to 4's language, from C++11: math text read into a term, which is evaluated, written back as text, rewritten and differentiated. It stands on parse/expression/ (gate G4). Its term, expr_term, is that module's expression<expr_op, expr_atom>: an operator applied to its operands, or an atom, which is a number (a math::value, with the literal it was written as, so that each type rounds the literal once), a variable or a named constant. A function is an operator of the term, so every fold and rewrite takes a call as it takes a sum. The six layers:

  1. tokens (token.hpp);
  2. the operator table and the parser layer (operator.hpp, parse.hpp);
  3. the term (term.hpp);
  4. the folds, to numbers and values (evaluate.hpp, with the function and constant tables of function_table.hpp, the arithmetic of arithmetic.hpp and the relations and logic of logic.hpp), to a program run many times (program.hpp), and to text (render.hpp);
  5. the rewrites (substitute.hpp, simplify.hpp, and Phase 4's derivative.hpp);
  6. the handle, math::expr (expr.hpp, which includes every header but reify.hpp).

Phase 3's kinds, complex_kind.hpp, quaternion_kind.hpp and matrix_kind.hpp, with matrix_function.hpp and rotation.hpp, and Phase 4's numeric.hpp, summation.hpp and antiderivative.hpp stand beside them, and reify.hpp, which makes a compile-time expression a term (step 32), math.hpp including it so that the language needs no compile-time core; expr_common.hpp's banner maps them all. A literal past every long double, or a fraction whose terms pass two words, is a range error until bignum exists. A decimal literal read straight into a float, double or long double goes through decimal.h, rounded once.

Comparing numbers as text. numeric_compare.hpp, a C++ face from C++98, compares two numbers written as text, in literal.h's syntax, exactly at any length: 0.1 is below 1/9, and 1e100000000000000000000 below 2e100000000000000000000. It reads them as rational_values, signed rationals of any size times a power of ten of any size, whose digits are integer_values in a std::string; until bignum, the C core has no arbitrary precision of its own. A text that is not a number, or a fraction over 0, is unordered with everything, as a NaN is.

4. Levels

Each face compiles from its floor and adds features as the language allows:

Level What the faces gain
