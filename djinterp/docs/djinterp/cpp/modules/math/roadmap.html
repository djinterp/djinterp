Principles

These are the owner's rulings. Each item below follows them.

  1. The C core is the foundation. Algorithms are written once in C. The C++ faces wrap them and add what each language level allows. Other element types take a generic C++ path. (2026.10.04)
  2. Every level gets everything it can express. Each language level supports the most functionality it can, gets every optimization it allows, and shares code with the other levels. (N1, 2026.10.13)
  3. Expression, function and calculus start at C++11. A runtime expression for C++98 comes later, if users need it. (N1)
  4. One answer. A call gives the same result at every language level, and the same result in constant evaluation as at run time. For the double family, rewritten function by function from 2026.11.16, that result is one result, the correctly rounded one, on every platform (ruling 2, 2026.11.16; G6), under eight rules: no long double inside; no C library calls; no fused multiply-add made by the compiler that changes a result, with a start-up self-test that says if one did; plain double arithmetic, so no x87; no dependence on a C library at all; correctly rounded; within 2 to 3 times st_math's speed; and C's standard answers outside the domain (NaN, plus or minus infinity). Until each other family's turn, the result is the correctly rounded one or the C library's. The plain formulas, the _fast forms among them, follow the build where it fuses (S415).
  5. Chaining. Wherever it is appropriate, an operation returns a value that the next operation can be applied to. Steps that can fail chain through result<T, E> with and_then. (decision 3)
  6. Eager by default. Laziness is an explicit opt-in type, available from C++11. A lazy evaluation performs the same operations in the same order as an eager one, so the bits do not change. (decision 2)
  7. _fast variants only on measured demand. Each is named, has a documented ulp bound, and is tested against the _c reference. A _fast variant is never a global build switch, which would break the one-definition rule. (decision 1)
  8. The generic value comes before further features. Any value type, bignum included once it exists, must fit without redesign. (decision 4)
  9. Bones before precision. The headers and their interfaces come first. Benchmarks and bignum come last. (decisions 5 and 6)
  10. Stay mergeable. The lane keeps its changes inside math/, c/math/ and their tests, so that the net lane and the others can merge back into master with few conflicts.

Phase 0 — Ground truth

Phase 1 — The generic value

Design (proposed; G1 to G3)

Two faces, as everywhere in this module.

  • Dynamic. One run-time type that can hold any number. A new hand-written C header, c/math/value.h (C99, and C++98 when compiled as C++), defines struct dj_math_value. A C++ class, math::value in math/value.hpp (C++98), wraps it. The expression evaluator, the parser's literals and the interpreter all use it.
  • Static. Templates over a number type, as linear algebra and interval already are. number_traits<T> and a promotion trait, common_number<A, B>, steer them (C++98). A bignum type joins by specializing the traits.

Kinds. Every value has a kind.

  • Inline kinds are stored in the value, with no allocation:
    • none;
    • error: domain, pole, range or invalid;
    • boolean;
    • integer: exact, dj_math_imax;
    • rational: exact, reduced, a pair of dj_math_imax;
    • float, double, long double.
  • Boxed kinds come from a registry. Each registered kind supplies a table of operations: its name, its place in the tower, retain and release, arithmetic, comparison, conversion and text. Bigint, big rational, big float, complex, interval, vector and matrix will all be boxed kinds. Registering one changes neither value.h's interface nor the inline kinds' code.

The tower. The order is integer, then rational, then float, double, long double, then big float at a precision p.

  • Exact operations stay exact when the result can be represented. +, - and * on integers give an integer. / gives a rational, so 1/3 + 1/6 is exactly 1/2.
  • Exact combined with inexact gives an inexact result in the inexact operand's format. Two inexact operands give the wider format.
  • Transcendental functions of exact arguments are inexact. They are computed in the context's format, double by default.
  • When an operation involves a boxed kind, the operand higher in the tower handles it and converts the other operand. This is the same protocol as Ruby's coerce and Python's reflected operators.

Context. A context carries the precision for big floats, the rounding mode (round to nearest, ties to even, by default) and the error policy (errors as values, or a flag). It is passed explicitly, as in MPFR. There is no global state.

Literals. Text is read exactly:

  • 42 is an integer;
  • 0.1, 1e-3 and 2/3 are rationals;
  • a literal too long for two dj_math_imax becomes the nearest long double, until bignum exists.

Converting a rational to float, double or long double is correctly rounded: d_rational_to_f, _to_d and _to_ld (chunk 17), constant expressions from C++14, so each type rounds a literal once.

Errors. Float kinds follow IEEE 754, as the C core does: NaN and plus or minus infinity. Exact kinds have no NaN, so 1/0 and 0/0 on exact kinds give an error value (pole, invalid). The error policy can choose a flag plus a NaN instead.

Phase 2 — The expression bones: parse, evaluate, print

Design (proposed; G4, G5)

Layers. The language is built in six layers:

  1. Tokens. Math text becomes numbers, names, operators, brackets, commas and semicolons.
  2. Grammar. A math operator table (parse/expression's operator_signature) and a math-local parser layer. That layer adds what the shared parser lacks: calls with argument lists, vector and matrix literals, and telling unary minus from binary minus by position.
  3. Term. parse/expression's expression<math_op, math_atom>. An atom is a literal value, a variable or a named constant.
  4. Folds.
    • evaluate<T> for float, double and long double: typed and fast, with each literal rounded once and functions taken from the C core.
    • evaluate(context): gives a value, exact where possible.
    • render: back to text.
  5. Rewrites. Substitution, simplification (rules applied to a fixed point), and the derivative (Phase 4).
  6. The handle. math::expr, which wraps all of the above in chainable members.

What the shared parser does today. This was measured with chunk 12's probe, _handoffs/math98_chunk12_2026.10.13/, with P0's fixes applied:

  • It parses, prints and evaluates these correctly: 2 * x ^ 2 + 1, -x ^ 2 (that is -4 at x = 2), 2 ^ 3 ^ 2 (512), and sin(x) ^ 2 + cos(x) ^ 2.
  • It rejects atan2(1, x), [1, 2, 3], 2x and |x - 3|.
  • It prints a function as a prefix operator, sin x ^ 2, which a person reads as sin(x²).
  • Its operator lookup cannot see position, so the probe had to track whether a minus was unary or binary itself.
  • It reads no nullary operator back, though the renderer prints one, and it groups a non-associative chain, a = b = c, to the right rather than refusing it (chunk 27's record, section 6). A constant is an atom here, and 2d (chunk 31) reads a chain of relations as the conjunction of its links.

The table first listed the relations loosest, above logic, which would have read its own example x > 0 and x < 1 as x > (0 and x) < 1. 2d (chunk 31) put logic below the relations, as C, Python and Mathematica have it, so that not x = y is not (x = y) (S213), and reads a chain a < b <= c as a < b and b <= c, as Python and mathematics do (S214). The table first put ' beside !, tighter than ^, which would have read A^2' as A^(2'), that is A^2, where MATLAB, whose ' the language takes, reads (A^2)'. 3b (chunk 35) put the transpose between the unary minus and ^, so that A^2' is (A^2)' and A'^2 is (A')^2, as MATLAB reads both (S252).

Further conventions:

  • log is the natural logarithm, as in C. log10 and log2 are separate functions.
  • The constants are pi and e, and the booleans true and false.
  • Piecewise functions are written in function.hpp's vocabulary: piecewise(when(x < 0, -x), otherwise(x)).
  • ' is the transpose, as in MATLAB. Derivatives are written with diff.
  • Calculus is written as functions: diff(f, x), diff(f, x, n), int(f, x), int(f, x, a, b), sum(f, k, a, b), prod(f, k, a, b), lim(f, x, a), taylor(f, x, a, n).
  • Linear algebra is written as [1, 2, 3] and [1, 2; 3, 4], A * B, A', and functions: det, inv, solve, dot, cross, norm, trace, eig.

The handle (chaining, decision 3). Names are provisional:

math::expr  f = math::parse("x^2 * sin(x)");
double      d = f.diff("x").simplify().eval<double>(math::at("x", 2.0));
std::string s = f.diff("x").simplify().str();    // "2*x*sin(x) + x^2*cos(x)"
math::value q = math::parse("1/3 + 1/6").eval(); // exactly 1/2
math::expr  g = f.subs("x", math::parse("t + 1"));
auto        r = math::try_parse(text).map(       // result<expr, parse_error>
    [](const math::expr& e) { return e.diff("x"); });

Each member returns a new expr, so every step chains. A value chains the same way: v.abs().sqrt(), and for linear algebra A.transpose().inverse().

2e (chunk 32) made the handle so, with what 2a's skeleton changed: a member that ends a chain in a number gives an expr_result, as every step that can fail does (principle 5), so that d above is an expr_result<double> and q an expr_result<value>, holding exactly 1/2. A handle holding an error passes it through every member after it, and str() is then its message; of a term, str() writes as the renderer does, x ^ 2 * sin(x).
