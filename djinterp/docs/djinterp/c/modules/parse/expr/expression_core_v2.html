0. What this settles

The parser holds postfix operators with operands, and calls. A call f(a, b) and an index A[i, j] are roles of their opening bracket after an operand, at a precedence the language's table gives (math: 100), and their arguments are parsed in the same pass, with diagnostics at the character. The transpose A' and the factorial n! are postfix roles at their own precedences. (a + b)[1], A'[1], f(x)[1] and A[1][2] index any operand, as S252 asks, with no table beside the standard one and nothing put back after the parse. So for S190 the math session can choose core v2, and S209 and S252 then follow it: the parser layer's pass that reads calls and bars as atoms before the climb (S209) and the postfix table whose indices are put back after it (S252) are no longer needed once math moves onto core v2.

What else core v2 holds, each of which math's parser layer does by hand today:

The core is generic: it knows no language. Each client supplies a table of operators and roles, a token source, and, where it needs one, a hook; the core parses, reports, folds and renders.

2. What v1 cannot do

v1 is cpp/modules/parse/expression/: a term (expression<OpId, Atom>, the fixed point of one functor, over shared_ptr), its folds (cata), a renderer, a compile-time mirror, and a precedence climber (expression_parse.hpp). The climber's limits are the ones S190's review lists:

  • One role per token. op_of(token) returns one operator, and the climber decides prefix or infix from the descriptor, not from where the token stands; so a language with - both unary and binary must assign roles before the climb (chunk 12's probe).
  • Token offsets. parse_error carries the index of the token, not a character (chunk 27).
  • One kind of bracket, and no calls. is_open and is_close match any open with any close; a call, an index, a pair of bars or a literal has no form, so each is read before the climb and put back after (S209, S252).
  • No non-associative operators. DAssocNone climbs as right association (_right_min adds 1 only for DAssocLeft), so a == b == c parses silently as a == (b == c), and the CLI grammar's rule that it is an error is not kept.
  • Recursion. parse_nud and parse_climb recurse for every bracket and every prefix operator; S250 bought depth by moving work out of the recursing frame, and the depth is still the stack's.
  • One error. The first failure returns; nothing after it is seen.
  • C++11. Below it the header is empty; there is no C core and no C++98 face, so the parity law has nothing to test.

v1's term and folds are good and stay (section 15). What v2 replaces is the climber, and it adds the C core.

4. The term

4.1 Nodes

A term is a flat arena of nodes in an array, linked by index, with no pointers, so it copies, hashes and serialises whole, as the foundation's programs and grammars do.

struct dj_parse_expr_node
{
    uint8_t  kind;     // D_PARSE_EXPR_NODE_LEAF, _APPLY or _HOLE
    uint8_t  flags;    // D_PARSE_EXPR_NODE_GROUPED, _CHAIN, _JUXTAPOSED, ...
    uint16_t depth;    // its longest path to a leaf, 1 for a leaf,
                       // saturating at 65535 (section 6.6)
    uint32_t op;       // apply: its operator's id; leaf: its token class
    uint32_t first;    // apply: index of its first child in the args array;
                       // leaf: its token's value
    uint32_t count;    // apply: its number of children; leaf: 0
    uint32_t offset;   // its span's first byte: a group's open bracket
    uint32_t length;   // its span's length in bytes, its brackets included
};  // 24 bytes, asserted in both languages
struct dj_parse_expr_term
{
    struct dj_parse_expr_node* nodes;
    uint32_t                   node_count;
    uint32_t                   node_capacity;
    uint32_t*                  args;       // child indices, by node
    uint32_t                   arg_count;
    uint32_t                   arg_capacity;
    uint32_t                   root;
    uint32_t                   depth;      // the longest root-to-leaf path
    uint32_t                   flags;      // _OWNS_NODES, _OWNS_ARGS, _HAS_HOLES
};

Every value is 32 bits wide: a 64-bit integer does not exist at ISO strict C++98 on 32-bit targets, 64-bit Windows or macOS (re_std's rule), and the C++ face must compile there. A leaf's value is the language's: an index into its own table of atoms, an interned lexeme's offset, or a small integer.

4.2 Invariants

  1. Post-order. A node's children have lower indices than the node. The parser builds bottom-up, so this holds by construction, and d_parse_expr_term_verify checks it with the rest. A fold is therefore one pass over the array, in order, with no recursion and no stack.
  2. A DAG where a chain shares. a < b <= c is and(lt(a, b), le(b, c)) with b one node, the child of both links: S214's review's "the operand shared in the representation later". A fold in arena order computes b once. Nothing else shares.
  3. No node made by default. A missing operand is a hole node at the place it should have stood; the term carries _HAS_HOLES, and a fold refuses such a term unless its caller passes D_PARSE_EXPR_FOLD_HOLES.
  4. Spans cover their text. A node's span covers every token it was made from: a group's includes its brackets, a call's its callee and its closing bracket, a chain's join its first operand to its last.
  5. Groups leave no node. (a + b) is the node a + b with _GROUPED set and its span widened over the brackets, as S215 keeps it; folds and rewrites never step through a bracket node. A grouped leaf, (x), keeps its token's span, since a leaf's span is its text (the renderer's default atom writes it); the brackets are inside the span of whatever holds it, and a diagnostic about the group itself points at them.

4.3 Building and rewriting

The builder is public: d_parse_expr_term_leaf, d_parse_expr_term_apply (children by index), d_parse_expr_term_hole, d_parse_expr_term_copy (a subtree of one term into another, its nodes renumbered) and d_parse_expr_term_assign (a whole term into another, arena for arena, the face's copy; F38). A language's own pass after the parse (math's piecewise, a simplifier) writes a new term with these, as v1's rewrites write a new expression. Equality (d_parse_expr_term_equal, spans and _GROUPED ignored unless asked) and a digest (d_parse_expr_term_digest, fold.h: 32-bit FNV-1a over the subtree as a depth-first walk meets it, each node's kind, flags without _GROUPED, operator, number of children and a leaf's value, so spans and groups do not change it; F38) serve the parity tests and caches.

5. The signature

A signature is the language: its operators and, for each token class, its roles. It is built once, sealed (verified and indexed), and then read-only, so threads may share it.

5.1 Operators

struct dj_parse_expr_op
{
    uint32_t    id;          // the language's, not 0
    uint8_t     form;        // D_PARSE_EXPR_FORM_PREFIX, _INFIX, _POSTFIX,
                             // _MIXFIX
    uint8_t     assoc;       // _LEFT, _RIGHT, _NONE, _CHAIN
    uint16_t    flags;       // _FLATTEN, _WORD, _TRANSPARENT, _COMMUTATIVE,
                             // _ASSOCIATIVE, _IDEMPOTENT
    int32_t     precedence;  // larger binds tighter
    uint32_t    join;        // a chain's: the operator that joins its links
    const char* spelling;    // what the renderer writes
    struct dj_parse_expr_mixfix mixfix;  // a mixfix operator's parts
};
  • Prefix, infix and postfix are the classic forms.
  • Associativity is left, right, none or chain. none refuses a second operator of the same precedence beside the first (a == b == c and a < b == c in the CLI grammar). chain collects a < b <= c and joins its links with join (math: and).
  • _FLATTEN makes a repeated left-associative operator one n-ary node: a | b | c is pipe(a, b, c), as the interpreter's pipeline (interp/spine.hpp) is a sequence.
  • _WORD marks an operator spelled as a word (and, mod): the renderer spaces it, and it never starts a juxtaposed operand.
  • The algebraic flags (_COMMUTATIVE, _ASSOCIATIVE, _IDEMPOTENT) are v1's, carried for simplifiers.

5.2 Mixfix operators

A mixfix operator has more than one token: a call, an index, a group, a list, a pair of bars, ?:, if ... then ... else. One descriptor covers them all:

struct dj_parse_expr_mixfix
{
    uint8_t     lead;           // 1: it follows an operand (a call, an index,
                                // ?:); 0: it begins one (a group, a list)
    uint8_t     parts;          // its keyword tokens: 2 to 4
    uint8_t     list_hole;      // the hole between parts 0 and 1 is a list
    uint8_t     tail;           // an operand follows the last part (?:'s
                                // third, else's branch), at the precedence
    uint32_t    part[4];        // each keyword's token class
    const char* part_spelling[4];
    uint32_t    separator;      // the list's item separator class (`,`)
    uint32_t    row_separator;  // its row separator class (`;`), or 0
    const char* separator_spelling;      // what the renderer writes
    const char* row_separator_spelling;
    uint32_t    row_op;         // the operator of a row, where rows are seen
    uint32_t    rows_op;        // the operator of the whole, where rows are
    uint16_t    min_items;      // a list's bounds; max 0xFFFF for none
    uint16_t    max_items;
};

The holes between keywords are closed: each is parsed from precedence 0 up to the next keyword, so f(a + b, c) needs no brackets inside. A tail is open: it is parsed at the operator's precedence, so a ? b : c ? d : e is right-associative as C has it. The term of a mixfix operator is one apply node: its lead operand first, then its holes' items, then its tail. Math's call is call(f, a, b); its index index(A, i, j); its literal [1, 2; 3, 4] is matrix(row(1, 2), row(3, 4)) and [1, 2, 3] is vector(1, 2, 3) (rows_op and row_op, where a row separator is seen; the operator's own id where none is); ?: is cond(a, b, c). A _TRANSPARENT mixfix of one item is a group: (a) is a, flagged _GROUPED. Given a list hole (and no rows), it is a group for one item and its own node for any other count: awk's (i, j) in arr is in(group(i, j), arr), and a tuple is the same shape. The language's check refuses the node where it does not take one (F16).

5.3 Roles

A role says what a token class does in one position: in operand position (nothing before it ends an operand: the start, after an operator, after an open bracket or a separator) or in operator position (an operand ends just before it).

struct dj_parse_expr_role
{
    uint32_t cls;       // the token class
    uint8_t  position;  // D_PARSE_EXPR_OPERAND or D_PARSE_EXPR_OPERATOR
    uint8_t  kind;      // _ATOM, _OP (the op's form says which), _CUSTOM
    uint16_t flags;     // _CALLABLE, _CALLEE, _ADJACENT, _NO_JUXTAPOSE
    uint32_t op;        // the operator this token begins; a custom role's,
                        // the operator it reads as (below)
    uint32_t modes;     // the modes it is a role in; 0 for all
    uint32_t order;     // set when defined: roles are tried in this order
    dj_parse_expr_custom_fn custom;  // a _CUSTOM role's hook
    void*    custom_ctx;
};
  • An atom role makes a leaf; _CALLABLE marks a class that may stand before a call's bracket (math's names, not its numbers).
  • An op role begins its operator: a prefix operator or a mixfix one without a lead in operand position; an infix or postfix operator, or a mixfix one with a lead, in operator position.
  • _CALLEE on a lead mixfix role: only where the operand before it is an ungrouped leaf of a _CALLABLE class. Math: f(x) is a call, 2(y) and (x)(y) are not (S201), and with implied multiplication on they are products.
  • _ADJACENT: only where no space precedes the token (awk's call of a function of its own, f(x) but not f (x)).
  • Modes: a bit set. A parse runs in a mode, and a custom hook may run a sub-parse in another; a role whose modes miss it is not there. awk's print a > "f" reads its list in a mode without the relational >.
  • A class may have several roles in one position, tried in order; the first whose conditions hold is the one. A custom role that declines is passed over, and where no role takes a token in operator position, juxtaposition is tried next: so a ++ that declines after something that cannot be assigned begins the next operand, and awk's 1 ++i is concat(1, ++i).
  • A custom role in operator position may name an operator (op). It is then called after the frames that bind tighter than that operator are reduced, so its _left is the operand that operator would take: $i++ hands ++ the $i, and "a" "b" | getline hands | getline the whole concatenation (F15). With no operator named, it is given what is on top.
  • The closing tokens and separators need no role: a mixfix operator's parts declare them, and the parser knows which open operator expects which.

5.4 Juxtaposition

A signature may name one juxtaposition operator, an infix operator with no token. Where a token in operator position has no role there whose conditions hold, but has one in operand position, the parser applies the juxtaposition operator and reads the token as an operand. The language's hook, may_juxtapose(ctx, term, left, token), refuses where it must: math refuses between two numbers (S196); awk's concatenation takes it as it comes. A _NO_JUXTAPOSE role never begins a juxtaposed operand. Math's implied multiplication is the operator mul at 60, present only when G5's option is on (math builds two signatures, or one with the operator in a mode). The node is flagged _JUXTAPOSED, and its span covers both operands as any infix node's does (invariant 4); where a diagnostic needs the implied operator's place, it is the first byte of the operand it stands before, as math's implied * has the offset of the operand after it today.

5.5 Sealing

d_parse_expr_signature_seal checks the signature and indexes it. It refuses, with a diagnostic each: an operator id 0 or used twice; a form or an association that is not one of the four; a role whose operator is not defined, or whose form does not fit its position, an atom role in operator position, a custom role without a hook, a role for the end of the input; a chain whose join is not an infix operator; a mixfix with fewer than two parts or more than four, a part that is the end of the input, a list hole with min_items above max_items, rows whose operators are not defined, a _TRANSPARENT operator that is not a group, or has rows; a custom role that names an operator not defined; a juxtaposition operator that is not infix. An operator that no role begins is not refused: it is one only a hook builds (the command language's cmd), sealed and rendered by its form like any other. A closing part that is also an infix role is not refused: the order of section 6.2 reads it as the close wherever its operator is the innermost open, so an infix | inside a pair of bars needs brackets, as it does in every notation with both. Roles are sorted by class and position, and found by a binary search.

6. The parser

6.1 Tokens

struct dj_parse_expr_token
{
    uint32_t cls;     // the language's class; 0 is the end of the input
    uint32_t flags;   // D_PARSE_EXPR_TOKEN_SPACE_BEFORE, _LINE_BEFORE
    uint32_t offset;  // its first byte in the text
    uint32_t length;  // its bytes
    uint32_t value;   // the language's: what a leaf of it holds
};

Tokens come from a source, pulled one at a time:

struct dj_parse_expr_source
{
    int   (*next)(void*                       _ctx,
                  uint32_t                    _position,  // operand or operator
                  uint32_t                    _mode,
                  struct dj_parse_expr_token* _out);
    void* ctx;
};

The parser tells the source where it stands. That is what lets awk read / as a regular expression in operand position and as division in operator position, and math tell an opening bar from a closing one without a pass of its own. A language with a context-free lexer ignores the position; one with its tokens already in an array uses d_parse_expr_source_array. A source that fails (a character no token begins with) emits its own diagnostic, in its own domain, and returns the failure; the parse stops there.

6.2 The algorithm

Operator precedence over two explicit stacks, an operand stack of node indices and an operator stack of frames, in one pass over the tokens: the shunting-yard machine with Pratt's two positions. Each token is pushed and popped at most once, so the parse is linear in the tokens. Nothing recurses, so the depth is bounded by memory and by the guard, never by the C stack.

In operand position a token is:

  • an atom: a leaf is pushed, and the parser moves to operator position;
  • a prefix operator, or a mixfix one with no lead: a frame is pushed, and the parser stays in operand position;
  • a custom role: its hook is called (section 6.5);
  • the next part of the innermost open mixfix, a separator of its list, or the end: a hole is pushed and missing operand reported ((1 + ), [1, ], x[]), unless the open list is empty and takes zero items (f(), []); with D_PARSE_EXPR_OPTION_STOP, so is a token with no role in either position, which then ends the expression (below);
  • anything else: unexpected token.

In operator position a token is, in this order:

  1. the next part of the innermost open mixfix, or a separator of its list: the frames above it are reduced, and its hole or item is done;
  2. an infix or postfix operator, or a lead mixfix whose conditions hold: frames that bind tighter are reduced first (below), then an infix or lead mixfix frame is pushed and the parser moves to operand position, or a postfix node is built at once and the parser stays; a custom role is called, after the same reductions where it names its operator, and one that declines is passed over;
  3. a token with a role in operand position, where the signature has a juxtaposition operator and the hook allows: the juxtaposition operator is taken as an infix, and the token read in operand position;
  4. a closing part of an outer open operator: mismatched at the token, with a note at the innermost open part; the frames inside the outer one are closed, and the token read again as its part (a separator of an outer operator is step 8's: f((a, b))'s comma stands in a group, not in the call);
  5. the end: every frame is reduced; an open mixfix is unclosed, at its first part, the innermost one reported, as math has it; and, with D_PARSE_EXPR_OPTION_STOP, any token the expression cannot go on with, which is left unread in the result's next (F17): the ;, the newline, the ) of a statement's own if (, the next statement's word. Inside an open bracket it ends the parse the same way, and the bracket is unclosed; a closing part of another kind there is step 6's;
  6. a closing part that no open operator awaits, where one is open: mismatched, with the same note, and the token taken as the innermost one's close: (1 + 2] is one slip and one error, not an unopened and an unclosed;
  7. a closing part where nothing is open: unopened;
  8. anything else: unexpected token.

Reduction. On an infix or postfix operator of precedence p, the frames on top are reduced while they bind tighter: a frame of precedence q > p; or q == p and the incoming operator is left-associative; for none, q == p is non-associative, at the incoming operator, with a note at the frame's; for chain, q == p with a chain frame extends the chain. A prefix frame of precedence q is reduced while q > p, so a prefix operator takes into its operand every operator at least as tight as itself, as v1's climber does (-x ^ 2 is -(x ^ 2) with - at 70 and ^ at 80; -x * y is (-x) * y). A chain frame and a flattening frame collect their operands and build one node when reduced. Brackets are not reduced past: a mixfix frame stops the reduction, as a group does in every operator-precedence parser.

6.4 The command language's and awk's cases

  • a == b == c, a < b == c: non-associative at the second operator, with a note at the first, as the grammar's section III requires.

6.5 Hooks

Hooks are where a language does what no table can say. Each is a C function pointer with a context, and each is optional.

  • A custom role (_CUSTOM) is called with the parser, the token, and the operand before it (in operator position). It may peek at and take tokens (d_parse_expr_peek, d_parse_expr_take), build nodes into the parse's term (d_parse_expr_parser_term), report (d_parse_expr_report), run a sub-parse, or decline. peek and take read in a mode of the hook's (0 for the parse's; a mode is one bit, and a parse's own is 1 unless its options give another, so a hook's own is another bit, 2 or 4), so a hook can have its source read a block raw, as awk's is between its braces (F19); since the parser cannot read a token again, a hook takes what it read in another mode before it returns, and a hook that leaves one stops the parse. The nodes it builds may be of an operator no role begins, defined for its form and spelling so that the renderer writes it: the command, cmd, a flattening infix spelled "". It returns 1 with the node it made, 0 to decline (the token is then read as if the role were not there; what it peeked stays peeked), or -1 for a failure it has reported. A node it returns must be of the term and within the guard.
  • The sub-parse (d_parse_expr_sub, built 11-10) reads one expression inside a hook: (parser, floor, mode, &node), the operators taken those that bind tighter than floor (D_PARSE_EXPR_FLOOR_NONE for every one), in mode, ending without an error at the first token it cannot go on with, which stays read for the hook to peek. getline < file reads the file with the floor at concatenation: getline < f x is concat(getfile(f), x), and f(getline < g, x) ends the file at the comma. The floor holds only while no bracket of the sub-parse's own is open; inside one every operator is taken and every error is one, as in the parse. It runs on the parse's own stacks behind a barrier, so it allocates nothing of its own; it counts against the depth guard like any nesting, and its errors against the allowance. A hook that ran a sub-parse may not decline, since what it read cannot be read again: doing so stops the parse with a bad-argument failure, as a token left read in another mode does.
  • Modes in brackets (F18, built 11-10). A mixfix operator's hole_mode is the mode its holes are read in, one bit, 0 for the mode outside it. The parse switches to it at the opening part and back at the closing one; at its last part when it has a tail, so a tail is read in the mode outside. An end of input is read in any mode.
  • may_juxtapose (section 5.4).
  • check is called on each apply node as it is built, with its span; it may refuse it with a diagnostic of the language's domain. Math's when and otherwise outside piecewise, an index of three indices, a literal's rows of different lengths.

6.6 The depth guard

depth is the term's longest path from the root to a leaf, kept as nodes are built (each node's in its depth). Past max_depth the parse reports too deep and stops: at the token that would open an operator past it (open operators nest at least as deep as the term they make), or at the operator whose node is built past it (a long left-nested chain opens nothing). A node's depth is 16 bits, so the guard is 1 to 65535, or D_PARSE_EXPR_DEPTH_UNBOUNDED; a value between is refused, knob and option both, as no node could record it. The core needs no guard, since nothing in it recurses; the guard is for what consumes the term and does recurse: v1's cata through the bridge, math's simplifier. S250's review asked for it, with the bound the owner's to set: the knob's default is 1000 (a 1 MB stack, Windows' default, holds that many of v1's cata frames with room to spare), the option overrides it, and D_PARSE_EXPR_DEPTH_UNBOUNDED leaves only memory.

7.2 Line and column

A span is bytes. d_parse_expr_locate(text, length, offset, &line, &column) gives the 1-based line, counting \n, \r\n and a lone \r each as one break, and the 1-based column in characters (Unicode code points, as the style guide counts a line's length). The lane G kit's d_cli_report_at takes them: g.vp:2:12: error: ... (cli-taken 80).

7.3 Which error first

The parse goes on after an error, so that it can find one further left that it only learns of later (a bracket never closed is known at the end, and placed at its opening). Recovery is plain: a missing operand becomes a hole; an unexpected token is skipped; a mismatched close closes the frames inside the one it matches, or, where none awaits it, closes the innermost; a non-associative pair is taken as left-associative; the end closes what is open. It stops after max_errors errors.

The result names one diagnostic as the error: by default the leftmost, which is math's rule ("of two errors the one further left is given", S209) and every compiler's. One difference from math's parser layer: today a bracket's error comes before a grammar error wherever it is, because brackets are matched in a pass of their own. 1 + * 2) is today unbalanced at the ), and with core v2 unexpected '*', which is further left. The option error_order keeps math's order where its tests need it: structure_first names the leftmost bracket error where there is one.

A fold is an algebra applied bottom-up: one pass over the arena in order, each node's value computed from its children's, held in an array of values the caller sizes (or the core allocates, under the heap knob).

Strict evaluation suits math's folds as they are (v1's cata is strict too); for the lazy case, and's second operand or piecewise's branches, there is the walk: depth first with an explicit stack, an enter that may skip a node's children (D_PARSE_EXPR_WALK_SKIP) or end the walk (D_PARSE_EXPR_WALK_STOP), and a leave. The command language skips a pipeline's later stages after its first failure, and and's right side after a false left, so f1 | b ; d still runs d; it stops only to abandon a script (lane G's probe of 11-10, seven cases under ASan and UBSan).

9. Rendering

d_parse_expr_render writes a term back as text, through a write function (size_t (*)(void*, const char*, size_t), which lane D's stream takes), or into a buffer as snprintf writes (d_parse_expr_render_buffer), with an atom writer for the leaves (by default, the leaf's span's text where the source is given and holds it, nothing for an empty span, and otherwise its value in decimal). It is iterative too, and the bracket rule below is the parser's own decision (one function, shared), so the two cannot drift.

Brackets are written where reading the text back would group otherwise:

  • the operand on an operator's left needs them where it is an infix or prefix node that binds looser than the operator, or as tightly on the wrong side (a right- or non-associative or chain operator);
  • the operand on its right needs them where it is an infix or postfix node that binds looser, or as tightly on the wrong side (a left- or non-associative or chain operator): A ^ (2'), a - (b - c);
  • a postfix node on the left and a prefix node on the right never need them, since nothing can reach into them: x'[1], 2 ^ -x; S252's rule for the index ("bare where the operand is a leaf, a call, a literal, an index or a postfix operator's") is this rule;
  • a mixfix node's holes never need them;
  • the rule looks at an operand's whole open edge, not only its top operator: in (a + not b) <= n the left operand's top operator, +, binds tighter than <=, but its right edge ends in the prefix not, looser than <=, which would take b <= n if the brackets went, so they stay.

A chain's join (_CHAIN) is written as the chain, a < b <= c; a flattened node with its operator between each operand; a juxtaposed node with the operator's spelling, so math's implied product is written 2 * x as the term holds a product, or, for an operator spelled "" (awk's concatenation), as a space, with brackets around a right operand that begins with a token that has a role in operator position (a (-1)). Options: keep the author's groups (_KEEP_GROUPS), and the spacing (_COMPACT: spaces only around words).

The renderer's promise, tested both ways: reading a rendered term gives the same term, spans and _GROUPED aside; and rendering a read text gives a text that reads as the same term.

10. The default scanner

Most clients need no lexer of their own. d_parse_expr_scan (scan.h, built 11-10, behind D_CFG_PARSE_EXPR_SCAN) binds a source to a text, a sealed signature and a configuration of class numbers, the caller's, so it fills dj_parse_expr_token as any source does and brings no record or numbering of its own:

  • blanks are skipped; a newline is a token of newline_class where that is not 0, a blank otherwise, and either way the next token carries D_PARSE_EXPR_TOKEN_LINE_BEFORE (after any blank, D_PARSE_EXPR_TOKEN_SPACE_BEFORE);
  • names ([A-Za-z_], and the bytes 0x80 and above, so UTF-8 names pass whole, then those and digits) are name_class;
  • numbers are digits, then a point and digits, then an exponent (e or E, a sign, digits), each part only where a digit follows it, so 3.e is 3 then . then e: number_class;
  • strings in " or ', a backslash keeping the byte after it, are string_class;
  • every spelling the signature gives an operator's token, a mixfix's parts and a list's separators, and the words the caller adds for tokens only its hooks read (getline, |), longest first, so <= before < and << before <; where two spell alike the caller's word comes first. A spelling in word characters (and) is the token only as a whole name: android is a name;
  • a byte that begins nothing, and a string never closed, is stray_class, which the parser reports as unexpected; with 0 the source fails there.

The source does not consult the position or the mode it is told, so a language whose tokens differ by either brings its own. Math keeps its own lexer (its numbers are decimal.h's grammar, S189), and the command language its own reader (its option shapes and word parts, G's P1 to P8); the scanner is for bitwisedom, the templates, vparse's notations and tests.

11. Control: knobs and options

Each setting that takes a default and an override is a knob that sets the default and an option that overrides it, the owner's rule, in lane E's knob-and-option pattern (agreed 11-05, its API frozen 11-13). Three are rows of a program-wide parse group, flat rows in a djin named parse (agreed with lane E 11-10: a scope in option_env is a context within a frame, not a group of names), each defaulting to its knob:

  • expr_max_depth: D_OPTION_ENV_INT_RANGE_KNOB_NAMED, 1 to 65535, with the named value unbounded (D_PARSE_EXPR_DEPTH_UNBOUNDED), which lane E's named INT rows bring in its window of 11-11;
  • expr_max_errors: D_OPTION_ENV_INT_RANGE_KNOB, 1 to 65535;
  • expr_error_order: D_OPTION_ENV_CHOICE_KNOB over leftmost (1) and structure_first (2), the values cfg_parse.h gives the knob;
  • diag_text, diag_facts and log (built 11-25): D_OPTION_ENV_BOOL_KNOB each, defaulting to D_CFG_PARSE_DIAG_TEXT, D_CFG_PARSE_DIAG_FACTS and D_CFG_PARSE_LOG: whether diagnostics carry their text and their facts, and whether parse's log unit attaches (section 7.1). Each chooses among what the build has: on, in a build without its facility, gives nothing, and the sink says so. A record reaches the log only where log is on and the log wants its code (log.level, log.parse_expr.level and its grade's level), so log off saves even gathering its facts.

So DJINTERP_PARSE_EXPR_MAX_DEPTH=unbounded and --parse.expr_error_order=structure_first work. An option of 0 means the setting in force, read through its cache when a parse starts; the group sits in a unit of parse's own (parse/settings.h, built 11-12), and a knob (D_CFG_PARSE_SETTINGS, default 1 or D_CFG_PARSE_ALL) compiles it out, 0 then meaning the knob again. D_PARSE_EXPR_OPTION_STOP gets no row: it is a caller's choice per parse, not a setting. The group is registered (d_parse_register(registry)) before a program starts its threads, and its header says so (promise 8); d_parse_unregister() takes it off again, and d_parse_djin() gives the djin to a caller that reads it.

The core does not call the option layer (F33). It reads the settings in force through one function, d_parse_expr_settings(&settings): the knobs, unless a reader has been installed with d_parse_expr_settings_from(reader), in which case the reader fills them and each value is checked as an option's would be, a value out of range falling back to its knob. d_parse_register installs the group's reader, which reads the three rows through their caches, and the diagnostics' reader of the last three (d_parse_diag_settings_from); d_parse_unregister takes both out. So a program that links the core alone links no option code, and a parse costs one call more than it did when 0 meant the knob.

12. Memory and sizes

Every allocation goes through d_parse_grow or one call of the caller's choosing, and every size is computed with d_ckd_mul and d_ckd_add before the call (promise 3). Counts are 32 bits; a text of 4 GiB or more, or a term of more than 2^32 - 1 nodes, is capacity, not a wrap. sizeof and offsetof of the node, the token and the term are asserted in the C headers, which the face includes at every C++ level (promise 3's layout gate): the node is 24 bytes, the token 20 with its offset at 8 and its value at 16, and the term's nodes and count lead it. Each of the face's classes that is its C structure (DOptions, DMixfix, DScanConfig, DRenderOptions) is asserted to add nothing to it.

13. The C++98 face

djinterp::parse::expr (inc/djinterp/cpp/modules/parse/expr/, built 11-12), at every level from ISO strict C++98 to C++26. Each class holds its C structure and calls the C functions, so nothing is computed twice and the parity tests compare like with like. The names are the C++ style guide's: classes D and Pascal case, functions and members in snake case (F34).

  • DSignature (signature.hpp): builder methods atom, token, prefix, infix, postfix, chain, mixfix, op, juxtapose, custom and role, each returning *this; a refused row leaves good() false and the chain goes on; seal(), sealed(), find(id) (once sealed). On the heap or in the caller's arrays; not copyable, movable from C++11. DMixfix builds a mixfix's descriptor: bracket, list, rows, with_tail, in.
  • DTerm (term.hpp): leaf, apply (an array, or from C++11 an initializer list), hole, copy, set_root, clear; nodes as DNodeView (kind, operator, value, children, span, flags, depth); verify, equal, digest, ==. On the heap or in the caller's storage; copyable at every level (by d_parse_expr_term_assign, good() false where the copy cannot be held), movable from C++11.
  • parse(signature, source, options, sink) (parse.hpp) returns a DResult: the term, the status, the error's domain, code, span and index, the token the parse ended at, and the diagnostics as DDiagnostic copies with their messages (F36), so a result is a plain value. With the caller's sink the diagnostics stay there. A source is a C source (the default scanner's, through DScanner), an array or vector of tokens, or any object with a next member of the C shape's arguments: a C++98 class, or a callable through make_source, a lambda from C++11. DOptions is the C options, zeroed.
  • fold<Value>(term, root, algebra, out, flags) (fold.hpp): the algebra any object with Value operator()(DNodeView, const Value* children, std::size_t count), the values held in a std::vector<Value>, each reached node once, in arena order, no recursion; walk(term, root, visitor) with enter and leave, depth first on an explicit stack. Both are C++ of their own over the same rules as the C fold and walk, not the C ones under a thunk, so an algebra or a visitor may throw (F35); the parity suite holds them to the C ones node for node.
  • render(signature, term, root, out, options) into a std::string, and render_to(..., writer) through any writer bool operator()(const char*, std::size_t), each with an optional C++ atom writer bool operator()(DNodeView, std::string&) (render.hpp); DRenderOptions is the C options, zeroed.
  • DScanner and DScanConfig (scan.hpp) bind the default scanner.

A source, a writer or an atom writer is called from inside the C parser or renderer; what it throws stops at the face and is a failure there (a fatal parse, a render that returns false), so no exception crosses a C frame (F37). expr.hpp is the umbrella for all of it.

Above C++98, and only as additions: move constructors and noexcept from C++11, lambdas and initializer lists from C++11. Nothing that changes a result depends on the level, and the suite says so at each one.

The bridge (bridge.hpp, C++11 and up, v1's floor; below it the file is empty): to_expression<OpId, Atom>(term, root, op_of, atom_of, out, flags) builds v1's expression<OpId, Atom> from a v2 subtree by the face's fold, each application through op_of(DNodeView) and each leaf through atom_of(DNodeView), so math's folds, its simplifier and lane D's layout keep their v1 term. 19. Decisions

Each with its alternatives; the recommendation is the one taken.

F1. The term is a flat arena in post-order, linked by index.

  • For: copies, hashes and serialises whole, as the foundation's programs and grammars do; a fold is one pass, with no recursion; a chain's shared operand is one node, folded once; C and C++ hold the same bytes, so parity is exact.
  • Against: a subtree is not a value of its own; a rewrite writes a new term, as v1's do anyway.
  • Alternative, a tree of pointers in C: each node allocated; no serialisation, and the depth bound by recursion again.
  • Alternative, v1's term in C++ over a C parser: no C term, so no C folds and no parity at the term.

F2. The parser is operator precedence over explicit stacks, with a role per token class and position.

  • For: linear, no recursion, any depth; roles by position are Pratt's, which every language here needs; mixfix and juxtaposition fit as frames; recovery is a local decision at each token.
  • Against: harder to read than a recursive Pratt parser.
  • Alternative, a recursive Pratt parser: simpler code, and the depth bound by the stack, which S250 spent a chunk working around.
  • Alternative, LR tables from parsegen: parsegen is preview, and a table needs a generator step before every change of a language's table.

F3. Diagnostics go into the foundation's sink, in a domain of their own, the leftmost error first, with recovery. For: one report per pipeline; the S209 rule made general. Against: math's bracket-first order changes, which the option keeps where needed. Alternative, the first error only: cheaper, and an unclosed bracket further left is missed.

F4. Tokens are pulled, and the source told the position. For: awk's /, math's bars and any lexer that must know whether an operand ends here. Against: a callback per token. Alternative, an array only: those lexers need a pass of their own again. The array form is given too.

F5. Names: d_parse_expr_, dj_parse_expr_, D_PARSE_EXPR_, djinterp::parse::expr, directories expr/. For: the siblings' pattern (d_parse_diag_, d_parse_machine_); D_EXPR_ is already the math lane's macro prefix (D_EXPR_RELATION_OP in math/function/function.hpp); expr/ keeps v2 apart from v1's expression/. Against: long names. Alternative, d_expr_ and expression/: shorter, and two prefixes and two generations in one directory.

F6. 32-bit values throughout. For: the face compiles at ISO strict C++98 on every target. Against: a leaf holds an index, not a pointer or a 64-bit number. Alternative, a 64-bit payload: the face then has a 64-bit floor, as pool.h has.

F7. A depth guard as a knob of 1000 and an option, over a core that needs none. For: S250's review; recursing consumers protected on a 1 MB stack. Against: a sum of more than 1000 terms is refused by default, and the option is the way past it. Alternative, unbounded by default: the core is safe, and v1's cata overflows a small stack on a deep enough term.

F8. v1's term and folds stay, as the C++11 algebraic view, with a bridge; its climber is deprecated in 0.8. For: math's folds and lane D's layout unchanged; math moves at its pace. Against: two term types until math's folds move. Alternative, retire v1 in 0.8: math and lane D rewrite in November.

F9. Style #80: one architecture, joined from the bottom (16, A).

F10. The depth guard is 1 to 65535, or unbounded. A node keeps its depth in the 16 bits its 24-byte layout has free. For: the node stays 24 bytes; no consumer that recurses can use a bound near 65535 frames on an ordinary stack. Against: no bound between 65536 and none can be asked for. Alternative, a 32-bit depth: the node grows to 28 bytes, a sixth more per node, for a range nobody uses. Alternative, a guard above 65535 clamped or read as none: silent, and it either refuses terms the caller allowed or drops the protection asked for.

F11. A closing part that nothing open awaits, inside an open operator, is one mismatched error, and closes the innermost. For: one slip, one error, at the character ((1 + 2]), and the parse goes on in step with the text. Against: where the writer left out an opening bracket, the close lands on the wrong one; the note at the innermost open part shows which. Alternative, unopened at the token and unclosed at the end: two errors for one slip, the second far from it.

Five more came of the lanes' review on 11-05 (H, E, G).

F15. A custom role in operator position may name its operator, and is then called after the reductions that operator would make. For: the hook is given the operand the operator would take ($i++'s $i, the whole concatenation before | getline) with no parser internals in its hands; a role naming no operator behaves as before. Against: a hook that declines leaves those reductions made; they are the ones any looser operator would make next, so only a later role of the same class at a tighter precedence could tell, and roles are tried in their order. Alternative, a predicate on operator roles: the same question of what the predicate sees, and a second way to write what a custom role already is. Alternative, a reduce call in the hook interface: every hook then reasons about frames.

F16. A transparent operator with a list hole is a group for one item and its own node for any other count. For: (a) stays the bracket-free node of invariant 5, and awk's (i, j) (a tuple, elsewhere) is a node a check can place. Against: one operator id for two shapes; a fold tells them apart by the node's kind, a leaf or an application of the group's id. Alternative, two operators on (: the parser would have to choose before it has seen the comma. Alternative, a node for every group: every client then steps through bracket nodes, which invariant 5 exists to spare it.

F17. D_PARSE_EXPR_OPTION_STOP ends an expression at a token it cannot go on with, and the result gives the token back. For: a statement's parser (awk's, the DSL's blocks, C's if () hands the core an expression and takes back the ;, the newline or the ), and the table, which already says what continues an expression, says what ends it. Against: a typo that would have been unexpected ends the expression instead, and the statement parser reports it. Alternative, the source ending the input there: the source cannot know what the table continues with, and the statement parser loses the token. Alternative, a set of ending classes per parse: each language lists its terminators and misses one at a time.

F18. A mixfix's holes are read in the mode it names (hole_mode, 0 for the mode outside). For: print (a > b) compares while print a > b redirects, by the table, and a sub-parse's mode reaches no further than its brackets. Against: one more field in the descriptor. Alternative, every bracket restoring the parse's first mode: wrong where the statement parser starts the parse in print's mode, as dawk's would. (Built 11-10, with the sub-parse.)

F19. peek and take read in a mode of the hook's, and a hook may not leave behind a token read in another mode. For: a source reads awk's block raw when a hook asks for it, unaware of hooks, as lane G recommends; the rule follows from a pull source, which cannot read a token twice. Against: a hook must take what it read raw. Alternative, the sub-parse's mode alone: a raw block is not an expression. Alternative, letting a hook change its source's state between takes: the source then knows of hooks, and the parser must promise how far it reads ahead.

F20 to F32 are the syntax layer's and the deliveries' (lane F's handoffs of 11-06 and 11-11). Eight more came of building the settings group and the face, 11-12.

F33. The core reads the settings in force through a reader it is given, and calls no option code. d_parse_expr_settings_from installs the reader; d_parse_register installs the parse group's. For: a program that links the core alone links no option layer, and the core's suite runs without one; the group is replaceable (a test's, an embedder's), and its values are checked where they are used. Against: one function pointer of program-wide state, written before threads start, as the group's registration already must be. Alternative, the core calling option_env itself: every client of the core links the option layer and its registry. Alternative, the caller passing the settings in each parse's options: every caller fetches them, and an option of 0 can no longer mean "the setting in force".

F34. The face's names are the C++ style guide's: classes D and Pascal case (DTerm, DSignature, DNodeView, DResult), functions in snake case (parse, fold, render_to). For: the guide's rule for classes, as the foundation's C++ follows it. Against: this design's draft names (term, node_view, result) move. Alternative, the draft's lower-case names: the guide keeps snake case for what the standard's protocols name, traits and re_std, and these are none of them.

F35. The face's fold and walk are C++ of their own over the C ones' rules, not the C fold and walk under a thunk. For: an algebra or a visitor may throw, and its exception unwinds no C frame; a value is any copyable type (a std::string, v1's term), not a byte size; neither recurses. Against: two implementations of one rule; the parity suite holds them to each other at every node of every text, with holes allowed and not, and a bad root. Alternative, a thunk over d_parse_expr_fold: values must then be trivially copyable bytes, and a throw must be caught at the thunk and the fold stopped, losing the exception.

F36. The face carries its own C++98 view of the diagnostics: a result copies each record and its message. For: a result is a plain value at every level, outliving the sink it came from; the foundation's diagnostic.hpp keeps its C++11 floor. Against: a copy per diagnostic; a caller who wants none passes its own sink, and the result then holds no copies. Alternative, bringing diagnostic.hpp down to C++98: another lane's header ported for a view that still could not outlive its sink.

F37. What a source, a writer or an atom writer throws stops at the face, and is that callback's failure. For: they are called from inside the C parser and renderer, whose frames an exception must not cross; the C shapes already have a failure (-1, a short write, false), and the face maps a throw onto it. Against: the exception's message is lost; a caller who needs it keeps it in the callback. Alternative, letting it through: undefined in C frames, and the parser's own state left behind.

F38. The C core gains d_parse_expr_term_assign and d_parse_expr_term_digest. For: the face's copy is the C arena copied whole, indices and unreached nodes too, so parity holds for copies; C clients (math's memo, lane G's caches) get the digest the face has, spans and groups not changing it. Against: two functions more in C. Alternative, the face copying by d_parse_expr_term_copy from the root: the nodes renumber, and a copy is no longer the same arena. Alternative, the digest in C++ only: C callers write their own.

F39. The bridge takes its ids and atoms from the caller, and leaves to it what v2 cannot take from one row. to_expression<OpId, Atom> maps each node through op_of and atom_of; from_operator_signature maps ids through id_of, flags a word's spelling, and counts the nullary and matchfix rows it leaves. For: v1's ids and atoms are any types, and v2's classes are the language's lexer's, which no v1 table names. Against: a language moving its table still writes its roles, and its constants and matchfix operators. Alternative, inventing classes and sealing: the classes would not be the lexer's. Alternative, a nullary row as an atom, a matchfix row as a mixfix: an atom needs a class, and a mixfix two parts where v1's row has one spelling.

F40. The face's suite is one module of three blocks, face, parity and bridge, at every C++ level, the bridge's tests skipped below C++11. For: one set of fixtures (the calculator built both ways, the C parse), as F25 has it for the syntax suites; a skipped test says why (F26). The C units it stands on are built once, at C99. Alternative, the three suites this design first named (t_parse_expr_cpp, t_parse_expr_parity and a bridge suite): three copies of the fixtures.
