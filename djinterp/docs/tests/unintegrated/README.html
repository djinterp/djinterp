Tests not yet in DTest

Every test here was written before it could use DTest, djinterp's test framework (c/modules/test and cpp/modules/test), and is kept as it is until it is ported. Nothing here uses DTest yet. Each runs today as it did before it moved here: the CI scripts in scripts/ci, CMake's test leaves and the Windows kits point at this folder.

The folder is laid out as tests/djinterp/ is: a C test under c/, a C++ one under cpp/, each below the module it tests. A test keeps its depth below the root, so its relative includes (../../../../../inc/...) resolve from here.

The database tests moved here on 2026.10.26 (git keeps their history as renames), and its C harnesses left again on 2026.11.10, as DTest suites in tests/djinterp/c/modules/db/<vendor>/ (CMake's c_<vendor>_tests and c_<vendor>_stubs_tests); its C++ harnesses are still here. The output stream's, its template engine's, the machine environment's and the environment printer's joined them from the stream's delivery of 2026.10.29, landed on the restructured layout in November. The stream's seven went into DTest on 2026.11.09, and the string's grow test on 2026.11.12; where each went is under "Ported" below.

How they behave, for whoever ports them

  • Each is a standalone program with its own main (database_tests's is its CMake runner): it prints a line per group and one per failed check, with the check's expression and line, ends with N checks, M failed, and exits 0 only when nothing failed.
  • Their checks are their own macros: D_TESTS_<VENDOR>_FACE_CHECK in the faces, D_TESTS_DB_CORE_CHECK and _THROWS in cpp/db (t_db_core.hpp), D_DB_CHECK in database_tests, and the stream's own in each of its three. A group is a function. The database's C suites, ported from harnesses of this shape, show one way: each group opens its test with the block of the header it tests, and records its checks with d_test_suite_check.
  • The servers come from the environment, never from the tests: DJINTERP_TEST_MARIADB_HOST, _PORT, _USER, _PASSWORD, _SOCKET; DJINTERP_TEST_POSTGRES_* likewise, with _DATABASE. Without a server the faces and cpp/db run only the checks that need none, and fail where DJINTERP_TEST_<VENDOR>_REQUIRED=1. Each makes and drops databases of its own, named for the run.
  • t_sqlite_core.cpp keeps its files in the folder its first argument names (. without one); the CI scripts pass . to every cpp/db harness.
  • What each group tests is in the comment above it ("Tests the following: ...").

When one is ported

Delete it here, and repoint what runs it: its script in scripts/ci, its CMake leaf under build/cmake/config/testing/, and its workflow under .github/workflows. A port at another depth below the root changes the relative includes too.
