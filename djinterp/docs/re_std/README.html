Three things to look at

<ratio> was broken. All 12 files had the core include mangled to // djinterp', '#include "../../core/djinterp.hpp"', ' — one line, entirely a comment, so none of them included djinterp.hpp. Looks like a Python list str()-ed into a replacement. Nothing compiled. Repaired and verified. Worth grepping the rest of the corpus for that signature; it's confined to ratio/ in this zip, but whatever produced it isn't.

re_std::byte{0x2A} does not back-port. Direct-list-initialising a scoped enum from an integer is P0138R2, a C++17 language change. The type reaches C++11 fine; only that spelling doesn't. C++11/14 callers write static_cast<byte>(0x2A), constexpr at every tier. No to_byte() factory was added to hide it — std has no such function, and inventing surface std lacks would break portability in the other direction. Recorded as a language ceiling in cstddef.json.

<chrono> days/months/years are fixed-length durations. t + years(1) advances by the mean Gregorian year (31556952s), not to the same date next year. The shipped d and y literals are the duration forms; when the calendar lands, 15d and 2020y become ambiguous with chrono::day / chrono::year and the literals will need splitting by context. Recorded in the new roadmap entry (priority 39) rather than worked around.

The comparables exposed a real inconsistency in <compare>. My first version failed on int. Cause: re_std::partial_ordering is re_std's own class (back-ported to C++11), but operator<=> is a language feature that can only ever yield std::strong_ordering. Folding a std category against an re_std one gives void, so the concept matched nothing. The concepts therefore take std:: category arguments — which matches compare_three_way_result, whose own docs already say it yields std::strong_ordering. Worth a decision: re_std owns four category types the language will never produce.

Also corrected in compare.json: both concepts were catalogued at a C++11 floor. That was wrong twice — the files didn't exist, and the tier is unreachable in principle. Now C++20 with a failure_reason.

Close-out: optional + ranges

All 27 umbrellas compile at all five tiers — 135/135.

<optional> — a function called three times and defined nowhere

internal::throw_bad_optional_access() had no definition in the corpus. Written into bad_optional_access.hpp, next to the exception it raises.

Two decisions in it worth knowing:

  • A function, not a bare throw at each call site. value() is constexpr and its body is a conditional expression — engaged ? m_value : (throw_bad_optional_access(), m_value) — and a throw-expression is not a valid operand there before C++14. The call keeps the expression legal at every tier and puts the exceptions-disabled handling in one place.
  • Not marked D_CONSTEXPR. It never succeeds, so it can never appear in a successful constant evaluation; marking it constexpr would imply otherwise. The enclosing value() stays constexpr regardless.
  • With exceptions disabled it calls std::abort(). There is no value to return and no way to report; handing back a reference to disengaged storage would be strictly worse than a clean abort.

<ranges> — 28 C++11 conformance defects, all one root cause

ranges.json claims a C++11 floor for 59 symbols. The module did not compile at C++11 at all.

Every defect is hard-won rule 2 — on C++11 constexpr on a member function implies const — showing up as three different diagnostics:

symptom count why it looks different
cannot be overloaded 22 a non-const/const pair collapses to two identical signatures
increment of read-only location 5 a mutator with no const twin — no collision to diagnose, it just silently became const
constexpr constructor does not have empty body 1 C++11 requires an empty constexpr ctor body

The middle row is the one to remember: it produces no overload clash, so a collision-driven check misses it entirely. My first pass did exactly that and had to be extended.

Fixes were error-driven, not heuristic — tests/fix_rule2.py and fix_rule2b.py parse the compiler's own diagnostics and re-qualify only the functions it names, so free functions and already-const members are never touched. Files: view_interface, single_view, owning_view, reverse_view, take_while_view, join_view, as_rvalue_view, as_const_view, repeat_view, movable_box.

One self-inflicted error, caught and fixed: a blind string replace turned D_CONSTEXPR_INLINE into D_CONSTEXPR_CPP14_INLINE, a macro that does not exist — briefly breaking tiers that had been passing. The per-tier matrix caught it; a C++20-only check would not have.

Design decision recorded + warning cleanup

The <compare> category split is now documented, not just decided

Wrote the rule into compare/compare's header comment, where someone about to write an operator<=> will actually hit it:

Writing an operator<=> by hand on a class that must work at C++11 → return an re_std category, that is what they are for. Constraining on, or inspecting, the result of the builtin <=> → use std's, because the subject is decltype(a <=> b) and the language decides that.

The comment also records the failure mode, which is the dangerous part: common_comparison_category ranks re_std's categories only, so folding a std category against an re_std one falls through to void and a same_as check just fails. A constraint written with the wrong set does not misbehave loudly — it matches nothing. That is exactly how the first three_way_comparable came to reject int. Both rejected alternatives are recorded with their reasons.

A cycle I created, and what it revealed

Wiring the 21 orphaned type_traits into the umbrella exposed a latent three-way include cycle: invoke_result.hpp (type_traits) needs is_reference_wrapper (functional), which pulled the whole type_traits umbrella back, and reference_wrapper.hpp → invoke.hpp → is_reference_wrapper closed a second loop. Correction: the C++98 floor claim was false

Every failure_reason in this batch carried the line:

"core/djinterp.hpp hard-errors below C++11, so C++98 is not a reachable tier"

It is not true. djinterp.hpp contains nothing that hard-errors at C++98. Compiled at -std=c++98 -pedantic, exactly two constructs are post-C++98 and both are warnings at most: an anonymous variadic macro in D_NOEXCEPT_IF(...), and _Pragma in the long-long diagnostic pair.

RE_STD_AGENT_README says the opposite of the claim: "compiles on C++98 through C++26", with a macro table that degrades every C++11 feature (D_CONSTEXPR → empty, D_CONSTEXPR_INLINE → inline) and a review checklist of explicit C++98 idioms. Decisively, its known-issues table logs "any.hpp | Entire file gated on C++11; needs C++98 path | Planned work" — blanket C++11 gating is tracked as a defect, not an accepted floor.

Provenance. I checked rather than assumed: the sentence is verbatim pre-existing in bit.json (14×), numbers.json (13×) and memory.json (1×). I did not invent it — but I adopted it for 49 more fields without verifying a load-bearing claim about a file nobody in this working set has, and used it to justify gating 38 of 50 new files. The tell was in my own output: I never gated <climits> or <cfloat>, and both are C++98-clean and working.

The one real bug: the category split, again

<tuple>'s operator<=> failed with common_comparison_category_t<std::strong_ordering, std::strong_ordering> resolving to void — the exact hazard I documented this morning, now confirmed as a live defect rather than a design note.

It affected four modules: tuple, pair, array, variant. Each folded the results of the builtin <=> (which yields std:: categories) through re_std's fold, which ranks only re_std's categories. All four now use std::common_comparison_category_t, per the rule in compare/compare's header. pair, array and tuple verified working at C++20/23.

That is two separate live bugs from this one split in a single day. It is worth revisiting whether the four re_std category types should exist at all.
